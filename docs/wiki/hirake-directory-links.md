複数の場所にある `docs/` を 1 つの vault へシンボリックリンク（ジャンクション）で集めている構成を、走査（ファイルツリー・横断検索・グラフ・統計・構造クエリ・意味検索）が扱えるようにする仕組みと、その安全側の作り。

## 設定

既定では**リンクを辿らない**。`%LocalAppData%\Hirake\settings.json` に次を足して再起動したときだけ有効になる（設定 UI は無い → [[hirake-data-paths]]）。

```json
{ "FollowDirectoryLinks": true }
```

**設定が無効なときは、リンクを経由するフォルダ自体が開けない。** ファイルツリー・横断検索・仮想タブの 3 か所で「`FollowDirectoryLinks` を true にすると開けます」と案内する。

## なぜ既定で辿らないのか

リンクが `\\server\share` を指していると、**走査した瞬間に SMB 認証が飛ぶ**ため。Hirake は完全オフラインを前提にした表示専用ビューアで、フォルダを開いただけで資格情報が外へ出るのは前提に反する（→ [[hirake-knowledge-exploration]]）。

## 安全側の作り（設定のオン・オフに関係なく効く）

| 規則 | 理由 |
|---|---|
| **検査はパスのルート側から 1 要素ずつ行う** | 末端から遡ると、危険な祖先を判定する前にその祖先を経由した問い合わせが起き、そこでネットワークへ出てしまう |
| **リンクを見つけたら、残りの要素を飛び先に継ぎ足してルートからやり直す** | 飛び先がローカルに見えても、その祖先が UNC を指していることがある |
| **`ResolveLinkTarget` に `returnFinalTarget: true` を使わない** | UNC を指すリンクの解決結果が `C:\...\UNC\server\share` という**ローカル風のパスに化ける**。それを見て判定するとネットワーク先を辿ってしまう |
| **デバイスパスは `\\?\C:\` と `\\?\Volume{GUID}\` だけ許可** | `\\?\GLOBALROOT\Device\Mup\server\share` のように、UNC を名乗らずネットワークへ出る書き方がある |
| **リンクの飛び先は固定／リムーバブルドライブに限る** | 種別が判定できないものを通さない（fail-closed） |

> **実測**: 到達しない UNC（`\\192.0.2.1\share`）を指す祖先リンクの配下を判定させると、末端から問い合わせた場合は **42,196 ms**（SMB のタイムアウト待ち）、ルート側からだと **0 ms**。「判定より先にアクセスしている」ことは時間で観測できる。

## 走査も表示も実体のパスで行う

リンク経由のパスのままだと、同じ文書が二重に出たり、相互に指し合うリンクで走査が止まらなくなる。そのため**ツリーの表示・検索結果・ワークスペースの保存値はすべて実体のパス**になる。

`C:\vault\docs-a\x.md` ではなく、リンク先の `C:\repo-a\docs\x.md` として扱われる。

- ワークスペース／セッションにも実体のパスが保存される（→ [[hirake-workspaces]]）
- ただし**設定が無効なときはパスを読み替えない**。設定を入れていない利用者の表示を勝手に変えないため

## 案内を出してよい条件

拒否の理由は 4 つに分かれ、**「設定を有効にすると開けます」と案内してよいのは 1 つだけ**。

| 判定 | 意味 | 案内 |
|---|---|---|
| `Allowed` | 走査してよい | — |
| `BlockedByNetwork` | UNC・ネットワークドライブ・デバイスパス | **出さない**（設定を入れても開けないため嘘になる） |
| `BlockedByLink` | ローカルのリンク経由。設定で開ける | **出す** |
| `NotFound` | 実在しない・判定できない・壊れたリンク | 出さない |

設定が無効でも**リンクの解決は最後まで行う**。見つけた時点で打ち切ると、UNC を指すリンクや壊れたリンクまで `BlockedByLink` になり、同じ誤案内が出る。

## 脅威モデル（保証の範囲）

**防ぐのは「あらかじめ置かれた（静的な）リンクを辿って、意図せず SMB 認証を送ってしまうこと」だけ。**

走査している最中にリンクの向き先を書き換えられる競合（TOCTOU）は防げない。閉じるにはパスではなく、再解析ポイントを辿らないハンドルで開き、同じハンドルのまま扱う設計が要る（→ #59 で調査済み。`File.OpenHandle` は `FILE_FLAG_OPEN_REPARSE_POINT` を受け付けないため P/Invoke が必須で、列挙まで閉じるなら `ntdll` の非公式 API に依存する）。

**この区別を曖昧にしない。** 「TOCTOU 対応済み」と記録すると、実態より強い保証だと後から誤解される。

## リンクを張り替えて使う場合

`C:\vault\current` のようなリンクの**向き先を張り替えて参照先を切り替える**使い方をしている場合、
ワークスペースには**保存した時点の実体**が記録される。張り替えても、そのワークスペースは元の実体を開く。

「リンク名を安定した別名として使う」意図とは逆に働くので、その運用ならワークスペースを保存し直す必要がある。

## 対象外の経路

`hirake://open` は、設定に関係なく**リンクを経由するパスを拒否する**（→ [[hirake-uri-scheme]]）。ブラウザのリンクから叩かれる唯一の外部入力で、他の入口とは信頼度が違うため。

## 後方互換の実測

「経路にリンクがあるフォルダを設定なしでは開けなくする」変更（#61）の影響を、開発機で測った結果。

- よく使う場所（ドキュメント／デスクトップ／プロファイル／`LocalAppData`／OneDrive／開発フォルダ）の祖先に**リンクは 1 つも無し**
- `.md` を含むフォルダ **4,806 件**中、経路にリンクがあるのは **25 件**で、**すべて `node_modules`**（pnpm の symlink）。`node_modules` はもともと走査対象外

> ユーザープロファイルや Documents 自体をジャンクションで移設している環境では影響が出る。案内が出るので設定で復旧できる。
