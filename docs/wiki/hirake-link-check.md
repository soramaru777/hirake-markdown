移動・改名で切れたリンクと、どこからも参照されていないページを一覧するビュー（ISSUE #56、Ctrl+Shift+L）。**直さずに、場所を示すところまでを担う** → [[hirake-editing-boundary]]。

## 起点は「捨てるのをやめる」こと

依存グラフ（`LinkGraphService.Build`）は以前から全 Markdown を解析していたが、**解決できなかったリンクをその場で捨てていた**（`fileSet.TryGetValue` が false なら `continue`）。壊れたリンクの情報は解析の途中で失われていた。

そこを記録に変えただけで、**フォルダの再列挙も再解析も増えていない**。孤立ページも既存の `GetBacklinks(file).Count == 0` で出るため、新しい集計は要らない。

増えたのは、**走査集合に一致しなかったリンクについてだけ**行う安全確認（祖先のリンクを辿る検査）と存在確認。件数上限（2000）に達したあとは、この確認自体を打ち切る（壊れたリンクを大量に書かれても走り続けないため）。

```
LinkGraphService.Build（既存の 1 回の走査）
  ├ 解決できた       → forward / backward（従来の辺）
  ├ 解決できない     → BrokenLinks（今回追加。以前はここで continue）
  └ 中身を見ていない → UnreadableFileCount（2MB 超・読込失敗）
```

## 壊れた wikilink は自動では乗らなかった

ISSUE 起票時の見立ては「[[hirake-wikilinks]] が入れば、解決できない `[[...]]` も `LinkInline` として同じ経路で拾える」だった。**これは誤りだった。**

`WikiLinkParser` が `LinkInline` を作るのは**解決できたときだけ**で、解決できなかったものは原文をそのまま見せる `HtmlInline`（span）になる。`LinkInline` ではないため、リンク抽出を素通りしていた。

```
[[解決できた]]   → LinkInline            → 従来の経路で拾える
[[解決できない]] → HtmlInline(span)      → 拾えない ← 本来いちばん検出したいもの
```

そこで `HtmlInline` の派生型 `BrokenWikiLinkInline` を作り、「何を探して見つからなかったか」を型として残した。**描画結果は基底クラスと 1 バイトも変わらない**（Markdig のレンダラ選択は基底クラス一致で行われるため。実測で確認済み）。span の HTML を文字列として拾いクラス名で判別する方法は、title 属性の文言や HTML エスケープに依存して静かに壊れるため採らなかった。

## 未解決の理由は 4 つ

| 理由 | 表示 | 判定 |
|---|---|---|
| `TargetMissing` | リンク先が無い | 走査集合に無く、`File.Exists` も false |
| `OutsideRoot` | 走査範囲の外 | 走査集合に無いが実在する（ルート外・除外フォルダ） |
| `WikiLinkNotFound` | 索引に無い | `[[名前]]` に一致するファイルが索引に無い |
| `Unverifiable` | 確認できない | 上限で打ち切った・読みに行けない等で「無い」「外だ」と言い切れない |

理由は**推定したルートしだいで変わる**（`FindWorkspaceRoot` は親を最大 5 階層たどる）。そのため画面には常に走査範囲を出す。これが無いと、利用者は「範囲の外」が妥当かどうかを判断できない。

出すのは**ルートだけでなく走査条件そのもの**（上限 500 ファイル・32 階層、隠しフォルダ・ドット始まり・`node_modules` は除外）。ルートだけを見せると「ルートの中にあるのに範囲外」と読めてしまう。孤立ページも**この条件のもとで被リンク 0** という意味なので、コピーの見出しにも同じ条件を書く。

**上限で打ち切ったときは「範囲の外」と断定しない。** 走査を途中でやめた以上、実在するリンク先が「範囲の外だから見つからなかった」のか「範囲内だが未走査だった」のかは区別できない。区別できないものを断定するのは嘘になるので `Unverifiable`（確認できない）にする。同じ理由で、**打ち切り時の孤立ページ判定も確定値ではない**（未走査のページから参照されているかもしれない）。

この判定に**パスの前方一致は使わない**。列挙側はジャンクション・シンボリックリンクを実体パスへ解決して返すため、字面のルートと走査済みパスは別の名前空間になり得る（リンクで束ねた vault では前方一致が外れる → [[hirake-directory-links]]）。打ち切りの有無だけで決めれば、その食い違いに依存しない。

**判定は走査側と同じ検査（`FileTreeItem.CheckTraversal`）に通す。** 字面のパスだけを見ると、途中のフォルダがジャンクションで UNC を指している場合に気づけず、存在確認でそのまま SMB へ出る（[[hirake-directory-links]] と同じ罠）。祖先まで辿る検査の結果で決める。

| 検査の結果 | 扱い |
|---|---|
| ネットワーク（UNC・ネットワークドライブ） | 触らずに「走査範囲の外」 |
| ローカルのリンク越え（辿らない設定） | 「走査範囲の外」（飛び先は実在するが、走査集合には最初から入らない） |
| 通ったら、その**実体パス**で確認 | 下の存在確認へ |

同じ検査を**辺の生成にも使う**。走査側はリンクを実体パスへ直して集合に入れるのに、リンクの解決先は字面のままだった。リンクで束ねた vault では同じ実体を指していても一致せず、**辺が失われて「リンク切れ」と誤検出されていた**。字面で外れたら実体パスでもう一度引く。

**「無い」と「見に行けない」を混ぜない。** `File.Exists` はアクセス拒否も `false` に畳むため、読めないフォルダの中の文書が「リンク先が無い」と断定されてしまう。`File.GetAttributes` の例外で区別し、`UnauthorizedAccessException` / `IOException` は `Unverifiable` にする。

なお `[a](//host/share/x.md)` 形式は .NET の `Uri` が絶対 `file:` URI として解釈するため、**従来どおり外部 URL として無視される**（この ISSUE で規則は変えていない）。

## 誤検出させないための境界

対象は `LinkInline`（画像を除く）と、解決できない `[[...]]` だけ。次のものは従来どおり無視する。

| 書き方 | AST | 扱い |
|---|---|---|
| `![img](x.png)` | `LinkInline`（IsImage=true） | 対象外 |
| `<https://example.com>` | **`AutolinkInline`** | 対象外（`LinkInline` ではない） |
| `[a](https://…)` | `LinkInline` | 対象外（絶対 URI） |
| `[a](#section)` | `LinkInline` | 対象外（パス部が空） |
| `[a](x.pdf)` | `LinkInline` | 対象外（md 以外） |
| 自己リンク | — | 対象外 |
| `[[...]]`（設定でオフ） | 素のテキスト | 対象外（そもそも解析しない） |

## 黙って 0 件と言わない

「リンク切れ 0 件」が「本当に 0」なのか「見ていないだけ」なのかは、利用者から区別できない。**打ち切りは 0 件のときでも必ず画面に出す。**

| 上限 | 値 | 伝え方 |
|---|---|---|
| 走査ファイル数 | 500（`FolderSearchService.MaxFiles`） | `Truncated` |
| 記録するリンク切れ | 2000 件（`MaxBrokenLinks`） | `BrokenLinksCapped` |
| 保持する文字数 | 1 件 300 文字（省略記号込み） / 合計 400,000 文字 | 1 件は末尾を `…` に、合計は `BrokenLinksCapped` |
| 1 ファイルの大きさ | 2MB（`MaxFileBytes`） | `UnreadableFileCount` |
| 読めないフォルダ | — | `SkippedDirectoryCount` |
| コピーする文字数 | 1,000,000 | 切ったことを注記に出す |

コピーは**行単位で削り、注意書きは必ず残す**（文字の途中で切ると「上限に達した」という但し書きのほうが先に消える）。結果（成功 / 一部だけ / 失敗）はホストからビューへ返し、ボタンの表示で伝える。**黙って「コピーしました」と出すと、貼り付けるまで失敗に気づけない。**

`UnreadableFileCount` と `SkippedDirectoryCount` は今回見つかった見落としへの対処。**2MB 超のファイルと、読めないフォルダは以前から黙って飛ばされていた**（列挙側が `continue` するだけだった）。そこにある文書からのリンクは 1 本も見ていないのに、そのことがどこにも出ていなかった。

## 表示側の判断

- **孤立ページから `index.md` / `README.md` を既定で除く。** どの vault でも入口ページは必ず被リンク 0 になり、毎回ノイズになるため。ただしチェックボックスで戻せる（隠したままにはしない）
- **一覧のコピーは `hirake://open?path=...&line=...` 付きの TSV。** 壊れた箇所をそのまま外部エディタや AI へ渡すための受け渡し口 → [[hirake-uri-scheme]]
- クリップボードへの書き込みは `LinkCheckTab` だけが行う。基底の `DocumentTab` で受けると、生の HTML と script を書ける Markdown が任意にクリップボードを差し替えられることになる

## ついでに直した既存の穴

- リンク先に数十万文字を書くと `Path.GetFullPath` が `PathTooLongException` を投げ、**フォルダ全体の解析が落ちていた**（バックリンクパネル・ナレッジグラフを含む）。1 本のリンクのために全体を落とさないよう、そのリンクだけを対象外にする
- 走査側はリンクを実体パスへ直して集合に入れる（[[hirake-directory-links]]）のに、リンクの解決先は字面のままだった。**同じ実体を指していても一致せず、辺が失われていた**（バックリンクにも出ない）。上記の検査で実体パスへ直してから引くようにした

## 実測（開発機）

500 ファイル・リンク切れ 500 件の合成コーパスで、**構築 309〜382ms・保持 359KB**。`LinkGraph` はバックリンクパネルが 10 秒キャッシュで共有するため、太らせすぎていないかを確認した。行番号は表・入れ子リスト・引用・複数行段落の中でも、実際に書かれている行と一致した。
