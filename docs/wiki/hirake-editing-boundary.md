**Hirake はファイルを書き換えない。** その方針を保ったまま「読んでいて直したくなる」場面をどう扱うか、という判断をまとめたページ。

> **confidence: medium** — 方針は #55 / #56 で決定済みだが、**どちらも 2026-08-17 時点で未実装**。ここに書くのは決めたことであって、動作の記述ではない。

## 何が問題か

知識ベースとして Markdown を運用すると、人間の編集作業が必ず残る（規約を自分に合わせて直す、矛盾を裁定して書き戻す、一次資料を置く）。表示専用のビューアだけでは完結せず、**別のエディタを開く往復が毎回発生する**。

これは「編集機能が無いこと」の問題に見えるが、分解すると違う。

## 逆方向はすでに成立している

エディタ側で保存すれば、`FileSystemWatcher` による自動リロード（デバウンス + スクロール位置復元）で Hirake は追随する。**「編集 → 表示」は動いていて、欠けているのは「表示 → 編集」の一方向だけ。**

しかも Hirake は**読んでいる位置のソース行をすでに知っている**（「この位置へのリンクをコピー」が使っている経路）。行番号が外に出ていないだけだった。

つまり真の課題は「編集できないこと」ではなく **「行番号が外に出ていないこと」**。#55 はそこだけを埋める。

## 方針 1: 編集への遷移をつくる（#55・未実装）

読んでいる行を外部エディタの同じ行で開く。これが入ると、エディタ + Hirake のライブプレビュー運用が成立する。

### 特定のエディタを前提にしない

使うエディタは人によって大きく違い（VS Code / サクラエディタ / 秀丸 / EmEditor / Vim …）、行ジャンプの引数もそれぞれ異なる。そもそも行ジャンプを持たないエディタもある。テンプレート方式だけでは、**設定を手で書かせる時点で障壁になる**ため 3 段構えにする。

1. **プリセット** — 同梱 JSON。本体を更新しなくてもユーザーが追記・修正できることが重要（プリセットが誤っていても自力で直せる）
2. **自動検出** — `App Paths` レジストリと既知のインストール先。複数見つかるのが普通なので勝手に決めない
3. **カスタム** — exe と引数を自分で書く受け皿

### 引数は文字列でなく配列で持つ

```json
{ "name": "サクラエディタ", "exe": "sakura.exe",
  "args": ["-Y={line}", "{file}"], "supportsLine": true }
```

コマンドライン 1 本の文字列にすると Hirake 側で分解する必要が出て、パスに空白・`&`・日本語が含まれる場合の引用符処理を自前で持つことになる。配列なら `ProcessStartInfo.ArgumentList` に渡してエスケープを .NET に任せられる。日本語ファイル名が当たり前の環境なので、ここは効く。

### 罠: 「OS の既定アプリで開く」はフォールバックにならない

`.md` の既定プログラムは **Hirake 自身**であることが多い（`register.ps1` は既定が未設定なら Hirake を既定にする → [[hirake-file-association]]）。フォールバックにすると**自分がもう 1 タブ開くだけ**になる。「プログラムから開く」ダイアログを出すか、メニューを無効化して設定を促す。

## 方針 2: 壊れたものは直さず、見せる（#56・未実装）

ページの改名・移動でリンクは壊れるが、**リネーム時のリンク自動追従はやらない**。他ファイルへの書き込みが必要で、1 回のリネームで数十ファイルを書き換えることになり、失敗時の一貫性・自動リロードとの競合・文字コード保存の判断がすべて付いてくる。

**検出して場所を示すところまでを Hirake が担い、修正はエディタまたは AI が行う。**

前提として、`LinkGraphService.Build` は現在**解決できなかったリンクをその場で捨てている**。まず捨てるのをやめることが起点になる。[[hirake-wikilinks]] が入ったことで、未解決の `[[...]]` も同じ経路で拾える。

## 方針 3: AI への受け渡し口を使う

**これは今日から動く。** 実際に手を動かすのが人間ではなく AI である場面では、既存機能だけで完結する。

1. 直したい箇所までスクロールする
2. タブを右クリック →「この位置へのリンクをコピー」
3. チャットに貼って直させる

`hirake://open?path=...&line=42` にはパスと行番号が両方入っているため、受け取った側はファイルと該当箇所を特定できる。**このメニューは Hirake 同士のリンク用に作られたものだが、外部への受け渡し口としてそのまま使える** → [[hirake-uri-scheme]]。#56 の「一覧を `hirake://` 付きでコピー」は、この経路を一覧に広げる話。

## 唯一の例外候補（未決）

**タスクのチェックボックスのトグル**（`- [ ]` ↔ `- [x]`）。読みながら消し込む頻度が高く、構造クエリが既に `IsChecked` を持っているため実装は軽い。

ただし入れると「表示専用」を初めて崩す。1 文字の書き換えでも、書き込みが入れば自動リロードとの競合・書き込み失敗時の扱い・文字コード保存（UTF-8 / Shift-JIS フォールバック）の判断が付いてくる。**#55 を実際に使ってから決める。**
